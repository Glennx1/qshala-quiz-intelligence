# Alembic migrations

Added under Phase 4 of the priority plan. **Does not replace** `app/database.py`'s
`ensure_schema_columns()` — that function still runs on every boot, still creates every table
from scratch on a fresh environment (local dev, CI, a brand-new Postgres instance), and every
existing deployment already has every column it describes. It's left alone, frozen as legacy.

**Going forward, every new schema change should be an Alembic migration instead of a new tuple
appended to one of the hardcoded column lists in `ensure_schema_columns()`.** That function has
no history, no rollback, and silently swallows every error (`except: pass`) including real ones,
not just "column already exists." A migration is reviewable in a PR diff, has a real
`downgrade()`, and fails loudly instead of silently if something's wrong.

## One-time setup (do this once, on the real database, before anything else)

The production Neon database already has the schema this repo's models describe — built by
`ensure_schema_columns()` over many deploys, not by Alembic. Adopting Alembic on a database that
already has the target schema means **stamping** it, not **upgrading** it:

```bash
cd backend
pip install -r requirements.txt   # pulls in alembic
DATABASE_URL="<the real Neon connection string>" alembic stamp head
```

`alembic stamp head` writes one row to a new `alembic_version` table recording "this database is
at revision 0001_baseline" — it does **not** run `0001_baseline`'s `upgrade()` (which is a no-op
anyway) or touch any other table. Run this against the real `DATABASE_URL` exactly once. Until
it's run, `alembic upgrade head` run against that database would try to apply `0001_baseline`
(harmless, since it's a no-op) and then every migration after it in order — stamping first just
makes the history accurate from the start instead of relying on every future migration also
happening to be a no-op against existing data.

Also run it against any other long-lived database this app talks to (a staging DB, if one gets
set up later) before using Alembic against it.

## Going forward: writing a real migration

```bash
cd backend
alembic revision -m "add some_column to questions"
# edit the generated file under alembic/versions/ -- op.add_column(...), op.drop_column(...), etc.
alembic upgrade head      # apply it locally / against whichever DATABASE_URL is set
```

`alembic revision --autogenerate` will also work once there's a Python environment with this
repo's dependencies installed and a reachable database to diff against (neither was available in
the environment `0001_baseline` was written in, which is why that one was hand-written as a
no-op instead of autogenerated — see its own docstring). Always read an autogenerated migration
before trusting it; autogenerate is good at spotting *that* something changed, not always at
getting the exact DDL right (defaults, server-side computed columns, and index options in
particular are worth double-checking).

## What this does NOT do yet

- Migrations don't run automatically on deploy. Cloud Build's existing auto-deploy trigger
  doesn't know Alembic exists. Running `alembic upgrade head` is a manual step for now (or add it
  as a step in `deploy/sync-ingestion-job.cloudbuild.yaml` or a new Cloud Build step later, once
  there's an actual migration to run that way, not just the baseline).
- `ensure_schema_columns()` isn't being removed. It's legacy, frozen, and still runs on boot;
  removing it is a separate, more invasive change than this one.
